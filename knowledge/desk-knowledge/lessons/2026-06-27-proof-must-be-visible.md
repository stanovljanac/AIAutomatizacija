# Proof must be visible — show the work running, don't narrate the result

**Purpose:** this file exists to explain what a "proof" beat must look like on screen.
**When to read:** read this when scripting or storyboarding any demo/proof scene, or
choosing between one deep example and several shallow ones.
**Do not duplicate:** if writing about visible-run proof scenes or demo legibility,
extend this file instead of creating a new one.

## Finding

A proof/demo beat convinces only when the viewer **watches the work run on screen**
(input → running → verifiable result, ≥4s, mobile-legible); narrating the result over
a static visual reads as opinion — and in a Short, **one escalating chain beats three
parallel examples**.

## Evidence

- **2026-06-27 — video 009 script gate**: the owner approved the script only with
  mandated fixes — S4 as a *visible run* (messy rows → "Running…" live counter →
  39 ✔ / 1 ⚠ Review → invoice flips to Chased) and S5 collapsed from parallel examples
  into a single escalating error chain ([PROGRESS 2026-06-27](../../../docs/PROGRESS.md)).
- **2026-06-28 — video 009 render review**: the visible-run S4 (`MoneyLeakRun`) was
  the **only scene of 8 the owner kept** from the first render — direct evidence that
  the visible run, not the styling, carried the scene (see
  [title-card lesson](2026-06-28-title-card-scenes-get-rejected.md)).

## Decision

"Proof, not opinion": every proof beat shows the run on screen — visible input, a
running state, and a checkable outcome, held ≥4 seconds and legible on a phone. In
Shorts, build one escalating chain instead of parallel examples. Applies through the
strategist-scene standard in [MOTION_SPEC §0](../../../style/MOTION_SPEC.md);
`MoneyLeakRun` is the reference implementation.
