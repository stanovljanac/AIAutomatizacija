# A self-healing pass that runs on every turn-end must skip what it can't write, never abort the pass

**Purpose:** this file exists to explain why `applyPlan` in the lifecycle reconciler reports
and skips an invalid derived file instead of throwing (D-062).
**When to read:** read this before writing any automated pass that repairs state on a hook,
a cron, or any other unattended trigger — especially one that validates before writing.
**Do not duplicate:** if writing about fail-soft design in unattended repair passes, extend
this file instead of creating a new one.

## Finding

"Validate before writing, throw if invalid" is the right instinct for a one-shot command a
human is watching, and the wrong one for a pass that runs unattended on every turn-end. The
throw aborts the *whole* pass, so a **single pre-existing invalid file — one the pass never
even touched — freezes the repair of every item after it, forever and silently.** The
failure is permanent rather than transient: the bad file isn't going to fix itself, and the
gate has no reason to ever report it, because the exception is caught by the fail-open
wrapper that keeps the hook from breaking a turn.

The invariant worth protecting is "**never write an invalid document**", and skipping
protects it exactly as well as throwing. What throwing adds is not safety, it is collateral.

## Evidence

- **2026-07-25, the D-062 backfill's first real apply:** it wrote 4 of 15 files and stopped
  on `content/004-…/publish.json` (`/medium must be object` — `medium` is a filename there,
  a shape from before that schema tightened). A second legacy file, `007-…/publish.json`,
  predates the required `title_options`. Neither defect had anything to do with the status
  flip being projected onto them.
- Had this shipped as-is, `.claude/hooks/publish-close.mjs` would have called `applyPlan` on
  every turn-end, hit 004 first, and left the 9 videos after it unhealed indefinitely — while
  the hook's fail-open `catch` swallowed the reason.
- The same module already applied this rule everywhere else (an unparseable `publish.json` is
  still ingested; a broken `produced_subjects.json` — the machine mirror from
  [the subject map](2026-07-15-subject-map-stops-near-duplicates.md) — is warned about and left
  alone) — the write path was simply the one place the philosophy hadn't reached.

## Decision

`applyPlan` now warns, records the file in a returned `skipped[]`, and **continues**; the CLI
prints the skips loudly at the end of the run. The one exception stays strict: the ledger
itself is a document *we generate*, so an invalid one is a bug in our code, not drift in the
owner's data, and it should be loud. General rule: **in an unattended repair pass, per-item
failures are per-item — the blast radius of one bad input must never be the whole pass.** The
corollary is that skips have to surface somewhere a human reads, or fail-soft becomes
fail-silent.
