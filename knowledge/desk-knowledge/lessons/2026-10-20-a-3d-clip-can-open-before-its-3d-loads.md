# A 3D clip can record an empty canvas — at its head and inside it; scan every clip

**Purpose:** this file exists so that black frames in a HyperFrames 3D clip — at its first frame or
for 1-5 frames inside it — are recognised as an empty WebGL canvas, not a scene bug or a compositor
dropout, and so nobody removes the fix that fills them.
**When to read:** read when a rendered HF clip, or a cut, opens on black frames, or before changing
how `compile-hyperframes` normalises clips.
**Do not duplicate:** the fix and its numbers live in `pipeline/04-render/compile-hyperframes.mjs`
(`bootBlackFrames`, `interiorBlackRuns`, `buildNormaliseCommand`); this note holds only the why.


## Finding

1. **HyperFrames does not wait for an async import.** Every 3D scene loads Three.js with a dynamic
   `import()` (`HF3.boot`). The runtime marks the page render-ready once the GSAP timeline is
   discovered, so the frames it captures before that import resolves show an empty canvas.
2. **It is a race, so it comes and goes with load.** 026's final clips: s1, s3 and s4 opened on two
   black frames, the other thirteen on none. A draft portrait render made while a Remotion composite
   was running opened on sixteen. 025's s11 clip had one (the published 025 master was re-scanned on 2026-10-20: no frame below YAVG 25 survived). s1 is the video's first frame: the
   hook would have opened on black, against the "frame 0 is the topic" rule (D-068).
3. **The canvas also comes back empty INSIDE a clip.** The HUD (DOM) still draws, the 3D layer is
   black for 1-5 frames: 026 s3 (3 frames), s6 (5), s7, s14 (1 each), s9 (2 singles); 025 had five
   singles — and `repair-dropouts` repaired those in 025's master believing they were Remotion
   compositor dropouts. They were in the HF clips all along.
4. **Nothing caught the rest.** The dead-render guard looks for errors (there are none),
   `repair-dropouts` never flags the first frame and only flags SINGLE frames (a 3- or 5-frame run has
   a dark neighbour), and the frame gate samples mid-scene.

## Evidence

Luma (YAVG) of the first frames, 2026-10-20: `s1.0` 17, 17, 106.9, 110.0 …; `s3.0` 17.4, 17.4,
100.3 …; `s4.0` 17, 17, 102.6 …; the s9 portrait draft sixteen frames of 17 then 83.8. 025 `s11.0`:
one frame below 20. The first fix (`trim`, then `tpad=start`) silently produced a clip two frames
SHORT — `tpad` adds nothing to a stream with no frame rate; `fps` has to come first.

## Rule

- `compile-hyperframes` scans the head of every fresh clip and, when a run of near-black frames is
  followed by a jump to a lit frame, cuts the run and clones the first live frame into it — same
  frame count, so the clip still fits its scene window 1:1. A scene that genuinely opens dark ramps up
  and is left alone. The log says `FIX <scene> — N boot-black frame(s)`.
- The same pass fills short black runs inside the clip (`interiorBlackRuns`: ≤12 frames, both sides
  far brighter) with the frame before them — `select` + `fps`, frame count unchanged; logged as
  `FIX <scene> — empty 3D canvas at frame(s) …`.
- Clips rendered before the fix, or a master already composited: scan the WHOLE file for frames
  below YAVG 25, then fill them (026: `buildRepairArgs` from repair-dropouts with the frame list);
  count frames before and after.
