# KOS Architecture — folders, categories, indexes, PROJECT.md

> Read when creating instance folders or categories, writing `PROJECT.md`, or deciding
> where a piece of knowledge lives.

## 1. Two-folder model

```
knowledge/
├── bootstrap/            # THE STANDARD — portable, project-agnostic
│   ├── SYSTEM.md         #   entry point (<150 lines, Agent-Skills-compatible)
│   └── specs/            #   nine specs, each <300 lines
└── <instance>/           # THE INSTANCE — this project's knowledge
    ├── index.md          #   global map, <200 lines, the agent's first read
    ├── PROJECT.md        #   profile (see §4)
    └── <categories>/     #   created on demand (see §2)
```

- **The standard is code, the instance is data.** Never project-customize `bootstrap/`;
  project specifics belong in `PROJECT.md`. Upgrading the standard on a project =
  replacing `bootstrap/` with a newer version (its version lives in `SYSTEM.md`).
- **The instance folder name is a profile concern** — pick one per project
  (`desk-knowledge`, `acme-kb`, …) and record it in `PROJECT.md`. Everything else about
  the layout is fixed by this spec.
- One instance per project. Multiple instances mean the truth has forked.

## 2. Categories (create-on-demand)

Eight category folders are defined; **each is created the first time a note of that
type exists** — never upfront, never empty:

| Folder | Holds (`type`) | Notes |
|--------|----------------|-------|
| `concepts/` | `concept` | what something is |
| `patterns/` | `pattern` | a reusable way it's done (needs evidence — see `lifecycle.md`) |
| `decisions/` | `decision` | why something was chosen — **only if no external ADR log exists** (§4) |
| `lessons/` | `lesson` | insight from our own experience; files named `YYYY-MM-DD-<slug>.md` (date = when learned) |
| `experiments/` | `experiment` | a test we ran + results |
| `research/` | `research` | external findings, sourced + dated |
| `glossary/` | `glossary` | term definitions |
| `archive/` | any, `status: deprecated` | superseded originals with provenance |

There is **no `workflows/` category**: step-by-step procedures are Agent Skills
territory. A KOS note may *link to* a skill; it never restates one.

**Placement rule:** the folder follows the note's `type` (one primary type per file,
`metadata.md`). If a note seems to fit two categories, it's either two notes or the
type is wrong — decide before writing.

## 3. Index hierarchy

Navigation is index-first, two levels deep:

- **Global `index.md`** (instance root, hard cap 200 lines): what this instance is, a
  link to `PROJECT.md`, and a link to every category index. First read for any agent.
- **Category `index.md`** (one per category folder, hard cap 200 lines): one line per
  note — `- [Title](file.md) — hook`. The listing block is regenerated by
  `knowledge-lint --fix` between `<!-- AUTO-INDEX:BEGIN -->` / `<!-- AUTO-INDEX:END -->`
  markers; prose around the block is human/agent-written.
- Every note must be reachable from its category index; every category index from the
  global index (validator checks 5–6).

`index.md` and `PROJECT.md` are **infrastructure files**: they carry no note
frontmatter and no Purpose header; the size caps and link resolution still apply.

## 4. `PROJECT.md` — the instance profile

The only place project specifics live. Required sections:

1. **Goal** — what this project is and what its knowledge base is *for* (3–6 lines).
2. **Canonical map (in-place pointers)** — where knowledge that KOS does **not** own
   already lives: ADR/decision log, style canon, fact stores, procedures/skills, rubric
   code, journals. One table: *what → where → note*. KOS categories duplicated by an
   external canonical source stay unused (e.g. `decisions/` stays empty when the
   project has an ADR log — **one decision log per project**).
3. **Knowledge sources** — where the agent *looks for new* knowledge (the canonical map
   answers "where does it live"; sources answer "where do I look"). Group as:
   - **Primary — external signals** (analytics, user feedback, external research…)
   - **Primary — internal outputs** (QA reports, review scores, experiment results…)
   - **Internal harvest** (journals, auto-memory graduation — distill lessons *from*
     these; don't treat them as fresh signals)
   - **Secondary** (industry reports, competitor analysis, official platform docs)
4. **Local rules** — project-specific policies: who promotes to `canonical`, validator
   wiring (manual / hook / CI), instance folder name, anything the owner mandates.

## 5. Boundaries with neighboring systems

| System | Holds | KOS relationship |
|--------|-------|------------------|
| Agent Skills (`.claude/skills/` or equivalent) | procedures — *how to do* | KOS never stores workflows; skills may link into KOS for facts |
| Agent auto-memory | private, per-user notes | graduate durable, shareable facts → KOS; memory keeps user preferences/corrections |
| Project ADR log | canonical decisions | `PROJECT.md` points at it; KOS `decisions/` used only where none exists |
| Automated fact stores | volatile, source-backed key-value facts | stay as-is; KOS `research/` holds *narrative* findings, not key-value data |
| Project journal / progress log | chronological events | unchanged; `lessons/` distill *insights* out of it, never duplicate its timeline |

Rule of thumb: if another agent or a human should see it → KOS. How *this user* likes
to work → memory. How to *perform a task* → skill. Already canonical elsewhere → point.

## 6. Where a new piece of knowledge goes (decision list)

1. Is it a procedure? → skill, not KOS.
2. Is it about this user's preferences? → memory, not KOS.
3. Does a canonical source in `PROJECT.md`'s map already own it? → update *that* source
   (if permitted) or link to it; never fork it.
4. Does an existing note cover the topic? → **extend that note** (its "Do not
   duplicate" header names this rule); create nothing.
5. Otherwise → new note: pick `type` (`metadata.md`), place per §2, link per
   `linking.md`, list in the category index, run `knowledge-lint`.
